# Why Rust

Systems programming has long forced a choice between control and safety. Languages
in the C tradition give the programmer direct authority over memory layout and
lifetime, and in exchange hand them the entire class of bugs that flows from
getting that authority wrong: use-after-free, double-free, buffer overrun, data
race. Managed languages remove those bugs by removing the authority, paying for
it with a garbage collector and a runtime.

Rust rejects the premise of the trade. It offers the control of a systems
language, and it enforces memory safety at compile time through a static
discipline of *ownership* and *borrowing* [@matsakis2014]. There is no garbage
collector. There is no runtime to speak of. The checks happen once, in the
compiler, and cost nothing when the program runs.

The claim is not marketing. A team at the MPI for Software Systems built a
machine-checked proof of the soundness of Rust's type system and of the core
libraries that use `unsafe` internally [@jung2018], and later formalised the
aliasing model those libraries must respect [@jung2020]. Rust's safety guarantee
is one of the few in industrial language design with a formal foundation behind
it.

## The cost of memory unsafety

The practical case is easier to state. Microsoft reported that roughly 70% of
the security vulnerabilities it assigned a CVE each year stemmed from memory
safety errors [@msrc2019]. These are not exotic failures. They are the ordinary
result of asking humans to track, by hand, which pointers are still valid.

This guide assumes you can read one other programming language. It does not
assume you have written C or C++, though the chapter on ownership will land
differently if you have.
:::

## Hello, world

Rust's entry point is a function named `main`. The program in @lst:hello is
complete: there is no header to include and no class to wrap it in.

```{.rust #lst:hello caption="A complete Rust program"}
fn main() {
    println!("Hello, world!");
}
```

Two details are worth noticing immediately. `println!` ends in an exclamation
mark because it is a *macro*, not a function: it expands at compile time, which
is how it type-checks its format string. And there is no `return` statement,
because `main` returns the unit type `()` implicitly.

Build and run it with Cargo, Rust's build tool and package manager:

```{.bash #lst:cargo caption="Creating and running a new project with Cargo"}
cargo new hello
cd hello
cargo run
```

Cargo is not an optional extra. It handles dependency resolution, compilation,
testing, documentation generation and publishing, and essentially every Rust
project uses it [@klabnik2023].

## What the compiler knows

Consider @lst:borrowfail, which will not compile.

```{.rust #lst:borrowfail caption="A borrow-checker error, caught before the program ever runs"}
fn main() {
    let mut items = vec![1, 2, 3];
    let first = &items[0];   // immutable borrow starts here
    items.push(4);           // mutable borrow — rejected
    println!("{}", first);   // immutable borrow still live
}
```

`items.push(4)` may reallocate the vector's backing buffer, which would leave
`first` pointing at freed memory. In C++ this compiles cleanly and produces a
dangling reference that may or may not crash, depending on the allocator, the
day of the week, and whether you are demonstrating the program to someone
important. Rust rejects it at compile time with an error naming both borrows and
the line where each begins.

::: tip
Read Rust's error messages in full. They are unusually good, and they routinely
tell you the exact edit that fixes the problem. Running `rustc --explain E0502`
prints an extended explanation of any error code.
:::

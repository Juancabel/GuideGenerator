# Error Handling

Rust has no exceptions. A function that can fail says so in its return type, and
the caller cannot accidentally ignore it. This makes failure paths visible in
the signature rather than discoverable only by reading the implementation.

## `Option` and `Result`

Two enums carry almost all fallibility in Rust:

```{.rust #lst:enums caption="The two core enums, as defined in the standard library"}
enum Option<T> {
    None,
    Some(T),
}

enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

`Option<T>` models a value that may be absent. `Result<T, E>` models an
operation that may fail with an error of type `E`. Neither is special-cased by
the compiler; both are ordinary enums you could have written yourself.

Because absence is a variant rather than a sentinel, Rust has no null pointer
for safe references at all — the entire category of null-dereference bugs is
absent from safe code [@matsakis2014].

## Matching

`match` forces you to handle every variant. Omitting one is a compile error, not
a silent fallthrough.

```{.rust #lst:match caption="Exhaustive matching on a `Result`"}
use std::fs::File;

fn main() {
    match File::open("config.toml") {
        Ok(file) => println!("opened {file:?}"),
        Err(e)   => eprintln!("could not open config: {e}"),
    }
}
```

## The `?` operator

Matching at every call site is verbose. The `?` operator propagates an error to
the caller and otherwise unwraps the success value, as in @lst:question.

```{.rust #lst:question caption="Propagating errors with `?`"}
use std::fs;
use std::io;

fn read_config() -> Result<String, io::Error> {
    let contents = fs::read_to_string("config.toml")?;
    Ok(contents.trim().to_string())
}
```

The `?` in @lst:question is exactly equivalent to the `match` in
@lst:desugared. The sugar matters: it keeps the happy path readable while
leaving every failure point marked with a visible character.

```{.rust #lst:desugared caption="What `?` desugars to"}
let contents = match fs::read_to_string("config.toml") {
    Ok(c)  => c,
    Err(e) => return Err(From::from(e)),
};
```

::: danger
`unwrap()` and `expect()` convert an `Err` or `None` into a panic. They are
appropriate in tests, prototypes and cases where the failure is genuinely
impossible. Reaching for them to silence a compiler error in production code
reintroduces exactly the class of crash Rust is designed to prevent.
:::

## Choosing an error type

@tbl:errors summarises the usual choices.

| Situation | Recommended approach |
|-----------|----------------------|
| Application code | `anyhow::Result<T>` — one error type, easy context |
| Library code | A custom enum deriving `thiserror::Error` |
| Cannot fail | Return `T`, not `Result<T, E>` |

: Error-type conventions {#tbl:errors}

The distinction is about audience. A library's callers need to match on specific
failure modes, so the error type is part of the public API and should be a
deliberate enum. An application's errors mostly get logged or shown to a user,
so a single boxed type with good context is sufficient [@blandy2021].

::: tip
Whatever you choose, implement `std::error::Error` for it. That single trait is
what lets your error interoperate with `?`, with `Box<dyn Error>`, and with the
wider ecosystem [@rustref].
:::

# Ownership and Borrowing

Ownership is the idea the rest of Rust is built on. It is a small set of rules,
checked entirely at compile time, that determines when memory is freed without
anyone writing `free` and without a garbage collector deciding at runtime.

## The three rules

1. Every value has exactly one variable that *owns* it.
2. There can be only one owner at a time.
3. When the owner goes out of scope, the value is dropped.

That is the whole model. Everything else — moves, borrows, lifetimes — follows
from keeping those three statements true.

## Moves

Assigning a heap-allocated value to another variable does not copy it and does
not alias it. It *moves* ownership, and the original binding becomes unusable.

```{.rust #lst:move caption="A move invalidates the source binding"}
fn main() {
    let s1 = String::from("hello");
    let s2 = s1;              // ownership moves from s1 to s2

    println!("{}", s2);       // fine
    // println!("{}", s1);    // error[E0382]: borrow of moved value: `s1`
}
```

@fig:ownership shows what happens to the stack and heap across that assignment.
The pointer, length and capacity are copied; the heap buffer is not. Marking
`s1` invalid is what stops both variables from freeing the same buffer when the
scope ends.

![The `String` on the left is moved, not copied. Only the three-word header is duplicated; `s1` is then statically marked invalid so no double-free is possible.](img/ownership.svg){#fig:ownership width=88%}

::: warning
A move is not a performance concern. It compiles to the same register or stack
copy the equivalent C would perform. What changes is that the compiler tracks
which binding is live, and refuses to let you use the dead one.
:::

Types that are cheap and safe to duplicate — integers, floats, `bool`, `char`,
and tuples of such types — implement the `Copy` trait and are copied instead of
moved, as shown in @lst:copy.

```{.rust #lst:copy caption="`Copy` types are duplicated rather than moved"}
fn main() {
    let x = 5;
    let y = x;                // i32 is Copy — x is still valid

    println!("{x} and {y}");  // prints: 5 and 5
}
```

## Borrowing

Transferring ownership into every function that needs to read a value would be
unbearable. Borrowing lets a function take a *reference* without taking
ownership.

```{.rust #lst:borrow caption="Borrowing a value immutably"}
fn length(s: &String) -> usize {
    s.len()
}

fn main() {
    let s = String::from("hello");
    let n = length(&s);       // s is borrowed, not moved
    println!("{s} has length {n}");  // s is still usable here
}
```

The borrow checker enforces one rule about references, and it is the rule that
makes data races impossible:

> At any given time, you may have **either** one mutable reference **or** any
> number of immutable references to a particular value — never both.

@tbl:borrows summarises what that permits.

| Existing borrows | New `&T` | New `&mut T` |
|------------------|----------|--------------|
| none             | allowed  | allowed      |
| one or more `&T` | allowed  | rejected     |
| one `&mut T`     | rejected | rejected     |

: What the borrow checker allows {#tbl:borrows}

This is the same constraint that `restrict` expresses as a promise in C, except
that Rust verifies it rather than trusting it. The formal model of what that
guarantee means in the presence of `unsafe` code is developed in Stacked Borrows
[@jung2020].

## Lifetimes

A reference must never outlive the value it points at. Usually the compiler
infers this. When a function takes several references and returns one, it
sometimes cannot, and you annotate the relationship explicitly.

```{.rust #lst:lifetime caption="An explicit lifetime relating two inputs to the output"}
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

The annotation `'a` does not change how long anything lives. It states a
constraint the caller must satisfy: the returned reference is valid for the
shorter of the two input lifetimes. The compiler then checks every call site
against that contract [@blandy2021].

::: note
Lifetime annotations are the part of Rust that most often reads as noise at
first. They become quiet quickly: *lifetime elision* means the great majority of
functions need none at all, and the rules for when they are required are
mechanical and documented in the reference [@rustref].
:::
